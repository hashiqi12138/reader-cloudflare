## 为什么这件事不是「移植一个开源项目」

主流的小说阅读器都跑不在 Workers 上：

| 项目                              | 技术栈               | 能否上 Workers                        |
| --------------------------------- | -------------------- | ------------------------------------- |
| 阅读3.0 / Legado                  | Android + Kotlin     | 不能，是安卓 App                      |
| 阅读3服务器版（hectorqin/reader） | Kotlin + Spring Boot | 不能，JVM 且有状态                    |
| riowang88/reader                  | Python + FastAPI     | 不能                                  |
| any-reader                        | TypeScript           | 规则格式是 eso 源，与 Legado 生态不通 |

所以这里是**用 TypeScript 重写规则引擎**，前端后续自己写。好在书源规则是**声明式**的，
真正要复刻的是一套规则语法，而不是某个应用的内部实现。

## 一个绕不过去的硬约束

Cloudflare Workers **禁用 `eval()` 与 `new Function()`**，而 Legado 书源里的 `@js:` 规则、
`{{}}` 模板都是货真价实的 JS 代码。解决办法是外挂一个编译成 WASM 的 ECMAScript 引擎
（本项目用 QuickJS；Cloudflare 自己在 Kitesurf 里用的是 Rust 写的 Boa）。

Workers 上跑 QuickJS 有两个坑，都已处理：

1. **不能让 Emscripten 自己去取 `.wasm`**。Workers 没有文件系统，也禁止从字节编译 WASM，
   唯一可行的是让打包器处理一个**相对路径**的 `.wasm` import。因此
   `scripts/copy-quickjs-wasm.mjs` 会把 WASM 从 `node_modules` 复制到 `src/engine/`，
   并用 `newVariant()` 直接把手上的 `WebAssembly.Module` 交给 QuickJS。
2. **句柄必须自己 dispose**。`newFunction()` 返回的句柄归调用方所有，忘了释放会让
   runtime 销毁时断言失败（`list_empty(&rt->gc_obj_list)`），表现为整个请求 Aborted。

书源来自社区、内容不可控，所以沙箱按**不可信代码**对待：限制内存（8 MB）、栈（512 KB）、
脚本执行时间（1.2 s，靠 QuickJS 的中断回调实现超时）、网络请求次数（10 次）与整次求值总时限
（8 s，含网络等待），且每次执行新建 runtime、用完即销毁。

### 为什么用 asyncify 变体

Legado 的 `java.ajax()` 在书源脚本里是**当同步函数用**的（`var html = java.ajax(url)`），
底层却要真的去发请求。只有 QuickJS 的 asyncify 版本能做到「脚本里同步、宿主侧异步」：
执行到那里脚本会挂起，等 fetch 完成后恢复。

只装 asyncify 这一个变体，而不是同步/异步各装一份：asyncify 版同样能跑纯同步脚本，
「同步走 A、异步走 B」会让同一段规则在两种模式下行为不同（这类分歧极难排查），
而且体积更划算（1003 KB vs 两份 1494 KB）。

### 一个必须绕开的库缺陷

销毁沙箱时要**先 `delete globalThis.__host`**，否则整个请求会失败。原因是
quickjs-emscripten 0.32.0 在 `runtime.dispose()` 里的顺序有问题：它先把该 runtime
从回调表注销，再真正释放 runtime；而宿主函数此时还挂在全局对象上，QuickJS 释放它们时
回调进来找不到 runtime，抛 `QuickJSRuntime(rt = ...) not found when trying to free HostRef`。

这个报错发生在**脚本已经跑完之后**，却会让整次求值判失败。摘掉全局引用后，这些函数
引用计数立刻归零、在 runtime 尚存时就被释放干净。实测三种写法：不摘会抛错；
只调 `vm.dispose()` 不抛但少释放一层；摘掉再按正常顺序销毁则完全正常。
细节写在 `src/engine/js.ts` 的 `releaseHostBridge` 注释里。

## XPath 为什么是「适配层 + 现成实现」

XPath 不可能靠换个 XML 解析器来解决：真实网页充满未闭合标签、裸 `&`、大小写混乱的属性，
XML 严格解析必然报错。所以仍然用 cheerio（htmlparser2）解析 HTML，
只在外面套一层 W3C DOM 接口（`src/engine/xpath.ts`），让标准的 XPath 1.0 实现跑在这层之上。

拿到的是**完整 XPath 1.0 语义**（各轴、谓词、内置函数），而不是自己写一个"够用"的子集 ——
后者遇到没覆盖的写法极容易悄悄返回错数据，比直接报错危险得多。
同理，这里也**没有**做 XPath → CSS 翻译：翻译器覆盖不了 `contains()`、位置谓词和各种轴，
翻不出来就只能降级或猜，而猜错是静默的。

有一处语义必须刻意调整：**`//x` 会被改写成 `.//x`**。XPath 里 `//x` 是「从文档根往下找」，
但书源里它始终表示「从当前节点往下找」—— 字段规则是跑在搜索结果某一条上的，
若真按文档根解释，就会抓到整页里第一个匹配的 `<a>`，数据看起来"有"但全串了行。
作用在文档根上时两种写法等价，所以这一改写同时满足「整页规则」与「条目内规则」。

## 书源存在哪、怎么进来

书源分两类，合在一个注册表里对外提供：

| 来源   | 存哪   | 为什么                                                                       |
| ------ | ------ | ---------------------------------------------------------------------------- |
| 内置源 | 代码里 | 它们是代码的一部分，跟着版本走；放进库会出现「部署了新版本，库里还是旧定义」 |
| 用户源 | D1     | 数量不定、由用户增删，且要跨会话保留                                         |

内置的**测试站点**书源只在 `ENABLE_FIXTURE=true` 时才会出现。线上它是关闭的，
所以不会列出三个打不通的源让人以为引擎坏了 —— 那种「列出来但必然失败」的条目，
和静默返回空一样会误导排查。

导入接口直接吃 Legado 书源 JSON 原文（裸数组或 `{"sources":[...]}` 都行），
并且**逐条校验、逐条报告拒绝原因**：一份 500 条的书源里坏了两条，
用户需要知道是哪两条、为什么，而不是整体失败。导入只校验名字与地址是否可用 ——
规则对不对是运行期的事，导入期就判「规则是否有效」要把每条规则都跑一遍，
代价高且误报多，不如先收下，让它在搜索时按书源粒度报错。

同一个站点地址重复导入算**更新**（只刷新规则，保留用户改过的名字、分组与启用状态）：
重新导入一次不该把停用过的书源又叫醒。

身份的 id 里嵌着站点 URL（`user:https://...`），所以启停与删除的 id 走请求体/查询串
而不是路径参数 —— 放进路径就要处理 `%2F` 这类转义，而代理、CDN、日志对编码路径的处理
并不一致，很容易在某一跳被拆开。

## 前端

零依赖、无构建步骤：`public/` 直接作为静态资源发布。三个刻意的选择：

**一律不拼 HTML 字符串。** 书名、作者、正文全都来自第三方站点，用 `innerHTML` 等于
把外部内容当代码执行。所有外部文本都走 `textContent`（`public/app.js` 里的 `el()`）。

**路由用 hash 而不是 History API。** hash 不需要服务端配合回退，少一处「刷新页面 404」
的坑，也省掉一份 SPA 回退配置的维护。代价是地址里多个 `#`，对这个应用无所谓。

**不引任何外部资源。** 字体、图标、CSS 框架都不引，图标用字符（`←`、`×`）。
目标站点被墙或 CDN 抽风时页面照常能开，也方便离线开发。

界面上的错误一律**就地显示原因**，而不是只给一句「出错了」：搜索时每个书源单独报
自己的错误码，取不到正文时直接把规则报的错摆出来，导入时逐条列出哪几条被拒、为什么。
书源规则出问题的表现本来就是「结果不对」而不是「报错」，把原因藏起来会让排查变成猜。

**阅读区按 `kind` 分四种渲染**：文本段落、图片画廊、`<audio>` 播放器、下载按钮。
图片用 `loading="lazy"`，单张失败时就地说明是第几张 —— 一张图挂了不该让整话变空白，
也不该静默。媒体地址用的是服务端签发的 `/api/media/...`，前端不接触上游地址
（原因见「媒体类书源」）。

书架与阅读进度分两张表：移出书架时进度一并清掉（免得重新加回来时冒出一个莫名其妙的
阅读位置），但「清进度」和「移出书架」是两个独立动作，混在一张表里会让删除书架条目
隐式地顺带删掉别的东西。不在书架的书也会记进度 —— 否则「搜到一本书、读了两章、
再搜回来」就得从头翻。

### 书架按身份隔离

需求是「书架按用户隔离」。做法是**本机身份**：前端首次访问生成一串随机 token
存在 localStorage，之后每个请求带在 `x-reader-user` 头上；服务端把它当作 owner，
书架与阅读进度都以 `(owner, book_key)` 为主键。

几个刻意的决定：

- **不做用户名密码。** 要的是隔离，不是访问控制；随机 token 本身不可猜，隔离就已经成立。
  它同时是账号体系的地基：将来把 token 换成真正的会话即可，那几张表不用再动。
- **书源不隔离。** 书源是「这份实例怎么取网」的配置，属于部署者；书架才是使用者自己的数据。
  两者混着管，只会让「换个浏览器书架空了、书源却还在」这种预期外的行为变多。
- **缺身份头就报 400，不做默认用户兜底。** 兜底会让所有没带头的请求悄悄共用一份书架 ——
  看起来一切正常，实际在互相覆盖数据，是静默错数据里最难查的一种。

有两点使用者必须知道，所以**页脚把身份显示出来了**（并提供复制 / 切换）：

1. 换浏览器、换设备、或清了站点数据，看到的是另一份（空的）书架；
2. 想在另一台设备上接着读，把 token 复制过去、在那边「切换身份」粘进去即可。

另外要说清楚它**不是访问控制**：拿到 token 的人就能读写那份书架。它只走 HTTPS，
也不要当密码到处贴。真要挡住外人访问整个实例，得另外加一层（Cloudflare Access 或自建口令）。

迁移 `0003` 会把升级前那批没有归属的数据归到 `legacy` 名下保留 —— 当时确实只有一个使用者，
但无法确定新身份该是谁。直接丢掉不合适，所以宁可让它暂时「挂着」。
要认领的话执行一次 `UPDATE shelf SET owner = '<你的身份>' WHERE owner = 'legacy';`
（`reading_progress` 同理，两张表都要改，否则进度会跟书架对不上）。

### 大合集要分批导入

社区合集动辄好几 MB（yckceo 的精选合集 6.5 MB / 821 条），一次传不进去：
导入接口对单次请求体有上限，为的是护住 Worker 内存。前端因此按大小切片分批提交，
再把各批的结果合并成一份报告 —— 而不是把上限调大，那等于把风险让给线上。

## 媒体类书源（图片 / 音频 / 文件）

`bookSourceType` 决定 `ruleContent` 取回来的**是什么东西**，四种类型的语义完全不同：

| 类型 | 含义 | 正文从哪来                                                                           | 前端怎么呈现     |
| ---- | ---- | ------------------------------------------------------------------------------------ | ---------------- |
| 0    | 文本 | `ruleContent.content` 取正文文字                                                     | 段落             |
| 1    | 音频 | `ruleContent.content` 取一条音频直链；**不写 content 时章节地址本身就是直链**        | `<audio>` 播放器 |
| 2    | 图片 | `ruleContent.content` 取图片地址（`<img>` 标签或裸 URL，可用 `nextContentUrl` 翻页） | 图片画廊         |
| 3    | 文件 | **不用 content**：下载地址在 `ruleBookInfo.downloadUrls` 上，且通常没有目录          | 下载按钮         |

这四类原先一律走文本那条路，结果就是「读不出来」，而且症状各不相同：
图片源把 `<img src=...>` 当正文渲染成一屏标签源码；音频源显示成一条网址（或直接报
「未配置正文规则」）；文件源因为 content 是空对象而报错 —— 而真正的下载地址躺在
`downloadUrls` 里，根本没被读过。**根子不是四个 bug，是把四种东西当成了一种。**

### 媒体为什么必须由服务端代取

图片和音频不能把上游地址直接交给浏览器，三个原因各自都能让「读不出来」：

1. **防盗链**：图片 CDN 校验 Referer，而浏览器在 `<img>` 上只能带当前页面的 Referer。
2. **混合内容**：这些站点大量是 http，而我们部署在 https 上，浏览器直接拦掉 http 子资源。
3. **跨域**：`<audio>` 播放与探测需要 CORS 头，上游通常不给。

所以 `/api/content` 返回的媒体地址一律换成 `/api/media/<token>` 形式的**签名地址**，
由服务端带上书源自己的请求头（Referer 用书源站点的地址）去取，并把上游的流直接转发回来。

签名的作用是**别把它变成一个开放代理**：任何人都能拿它当免费中转、隐藏真实来源。
只有本站自己签发的地址才认，密钥在首次使用时随机生成存在 D1 里（`settings` 表），
因此不需要额外的部署配置 —— 也就不存在「忘了配密钥导致代理裸奔」这种事。

顺带的好处在响应头里：`Range` 会透传（音频才能拖进度条）、上游的 `Content-Range` /
`Accept-Ranges` 一并带回、文件源加 `Content-Disposition` 强制下载。
另外**只放行媒体类型**：若某个书源的「图片地址」其实指向一段 HTML，会被降级成
octet-stream 并强制下载，而不是以 `text/html` 在同源下执行 —— 同源脚本能读到
localStorage 里的身份令牌。

## 字段规则里的 `{{...}}` 模板

字段规则（`bookUrl`、`intro`、`chapterUrl` 这些）里可以写 `{{...}}`，
线上 816 条书源里共有 **939 处**。麻烦在于**里面既可能是规则、也可能是 JS 表达式**：

| 写法                      | 里面是什么        | 怎么求值                 |
| ------------------------- | ----------------- | ------------------------ |
| `{{$.id}}`                | 规则              | 用 JSONPath 在条目上取值 |
| `{{@@h1@text}}`           | 规则（冗余 `@`）  | 剥掉多余的 `@` 再当规则  |
| `{{@css:.title@text}}`    | 规则（显式指令）  | 当规则                   |
| `{{java.timeFormat(… )}}` | JS 表达式         | 进沙箱求值               |
| `{{baseUrl}}` / `{{key}}` | JS 表达式（全局） | 进沙箱求值               |
| `{{'字面量'}}`            | JS 表达式         | 进沙箱求值               |

判错的后果一样：拿 JS 去当规则求值、或反过来，都只会得到空串，**不报任何错**。
所以分类只认明确特征（`$` / `@css:` / `//` / 选择器形态 → 规则，其余 → JS），
判不出来时倾向 JS —— 那一侧求值失败只影响这一小段。

`@@` 那 214 处是「这是个规则」的冗余标记；剥的时候**不能把 `@css:` 这类指令自己的前缀剥掉**，
否则一条 CSS 规则会变成 `css:…`，直接失效。

### 展开之后还要不要当规则求值

这是更容易漏的另一半。看两条真实规则：

```
bookUrl: "/api/tracks/{{$.id}}"               展开后是 /api/tracks/1593234 → 直接就是值
tocUrl:  "{{baseUrl}}##/book/##/chapter/"     展开后还要套 `##` 正则链
```

前者展开后如果还当选择器去筛，只会得到空串 —— 症状正是「这个字段读不出来」。
判断依据是**骨架**：把 `{{...}}` 换成空串之后剩下的那部分，有 `@`、`##`、`//`
这类规则语法就继续当规则，否则展开结果就是最终值。

用骨架而不是展开结果来判断，是因为展开出来的值里可能正好含 `@`（简介里有个邮箱就够了），
拿它判断会把一段纯文本误当成规则。

## 分隔符不能切进 JS 与字面量里

`&&` / `||` / `%%` 是规则的同级连接符，`##` 是净化链的分隔符 —— 但它们在 JS 代码里
是运算符、在字符串里是内容。切进去的后果不是「报规则不支持」，而是：
**每一块看起来都「合法」，只是结果全不对**，而且报错会指向切开后的半截内容。

线上 816 条书源、19424 处规则里，有 **321 处**的连接符落在 JS 区域内部 —— 这些就是
不标出来就会被切碎的规则。三种形态都在里面：

| 形态                 | 例子                                      | 谁踩过                                         |
| -------------------- | ----------------------------------------- | ---------------------------------------------- |
| 整条是 `@js:`        | `@js:(function(){ if (a && b) … })()`     | 禁漫天堂API（四个字段全是）、听小说APP、思路客 |
| 连接符在 `<js>` 块内 | `<js>if (data.a \|\| data.b) …</js>`      | 书旗小说、微信读书、晋江文学                   |
| `选择器@js:代码`     | `#content@html@js:… result \|\| '兜底' …` | 鸟鸟韩漫、存书啦、塔读文学、品书斋             |

所以切分前先标出「哪些位置不该参与」：`@js:` 后面那段代码、`<js>…</js>` 整块、
方括号里的 JSONPath 过滤器、引号里的字符串。这段扫描在 `src/engine/ruleText.ts`，
是纯函数、能直接单测。

**反向约束同样重要：不许过度保护。** 同一批数据里有 1022 处规则**确实该被切分**
（其中 66 处同时含 JS 区域，例如 `选择器||选择器 <js>代码</js>`）——
标错方向会把本该切开的规则粘成一条，症状和切碎一样难查，只是这次是「多切」变「不切」。

这件事有两层验证，都在仓库里：单测钉住精选形态（`test/ruleText.test.ts`），
再有一个**全量扫描**把整份书源集合的每一条规则都过一遍
（`test/ruleSplitting.scan.test.ts`，默认跳过，用法见「验证」一节）。

两处特别的取舍：

1. **`@js:` 的代码结束在「第一个不在引号里的 `##`」。** 线上 456 条整条是 `@js:` 的规则里
   没有一条后面跟 `##`，但 291 条 `选择器@js:` 里有 22 条带净化链（`@js:代码##正则##替换`），
   所以代码不能一路吃到规则末尾。只看引号、不数括号层级 —— JS 里的括号在规则文本里
   未必配平，少认一个 `##` 只是净化链失效，多认一个会把代码切碎。
2. **切 `##` 时不跳过 `<js>` 块。** `<js>##正则##</js>` 是书源里合法的净化写法
   （把净化链写在 js 段里），跳掉它那些规则就不生效了 —— 而切连接符时必须跳。

## 列表规则：`@js:` 返回数组时

接口型书源（音频、漫画）的 `bookList` 大量写成整条 `@js:`，脚本自己发请求、
返回一个数组。**线上媒体类 92 条源里，`@js:` 整条的列表规则是最常见的一形态。**
这条路上有三处独立的坑，任何一处都会让「搜索一条都搜不到」，而且**全程不报错**：

| 坑                                           | 后果                                                                                        |
| -------------------------------------------- | ------------------------------------------------------------------------------------------- |
| `@js:` 被 `detectKind` 归进 JSOUP 简写       | `parseJsoupRule` 对它解析出**空步骤**，`selectNodes` 原样返回根节点 —— **整页变成一个条目** |
| 数组结果被 `sandboxResultToString` 换行 join | N 个条目只剩 **1 个**；对象数组还会退化成 `[object Object]`                                 |
| 条目的 `source` 沿用整页                     | `$.name` 在整页 JSON 的根节点上找键，**每个条目都取不到字段、全被丢掉**                     |

三处叠在一起的表现就是「接口明明返回了数据，却一条都搜不到」——
比报错更难查，因为没有错误信息可看。

修法是让「取字符串」那条路明确承担列表语义：JS 列表规则不进节点那条路、
数组按元素逐个返回、每个条目的 `source` 是**它自己的文本**。
返回 HTML 片段的条目照旧按 HTML 解析，后续 CSS 字段规则不受影响。

## URL 字段里的 JS

顶层 URL 字段（`searchUrl`）里可以直接写 JS —— 线上 816 条源里 **85 条**这么写，
比 `@js:` 写在规则里更隐蔽：**认不出来时不会报错，而是把脚本原文当成地址去请求**。

| 写法                           | 条数 | 例子                                                               |
| ------------------------------ | ---- | ------------------------------------------------------------------ |
| 整条 `@js:`                    | 64   | `@js:qmSearch(key, page)`、`@js:var b='…'; b + '/search?q=' + key` |
| 整条 `<js>…</js>`              | 17   | `<js>var u = '…'; if (page > 1) { u += '&p=' + page } u;</js>`     |
| 「地址 + 请求选项」再跟 `@js:` | 4    | `https://…/index.php,{…}\n@js:so = String(result).replace(…)`      |

第三种最容易看错：`@js:` **前面那段不是前缀**，而是喂给脚本的输入（脚本里读 `result`）。
把脚本结果拼回前缀后面，会得到一个「合法、能返回 200、但内容完全不是那个站」的地址。

两个顺序上的坑，都是线上脚本明确依赖的：

1. **请求选项要在脚本跑完之后再拆。** 脚本自己就会拼 `,{...}`（少年梦阅读、露西弗
   都这么写），先拆选项等于把脚本代码从中间切断。
2. **`{{}}` 展开要放在脚本之后。** 脚本的输入 `result` 是**没展开过的原文** ——
   全本同人小说网的脚本里就写着 `String(result).replace("{{key}}", key)`；
   而脚本的输出里还可能有 `{{page-1}}` 这种表达式，所以展开得再做一次。

另外：**脚本里必须有取网能力**。URL 字段的脚本经常要自己先发一次请求才知道真正的
地址在哪（米读小说要跟一次 302 拿新域名、小书本网要先把搜索页抓回来读 `form[action]`）。
缺了它脚本会报「java.ajax 不可用」——一个看起来与书源完全无关的错。

## 沙箱助手

沙箱里除了 `java.ajax` / `get` / `post` / `base64Encode` 这些，还实现了下面这些。
线上 816 条书源里，媒体类（音频 / 图片 / 文件）共 92 条，其中 **56 条**用到 `java.*`。

### `java.getString(规则[, 内容])`

在脚本里回过头去跑**一条引擎规则**，返回字符串。真实写法：

```
{{java.getString('$.freeStack')=='1'?'':'💲VIP'}}
{{java.timeFormat(java.getString('$.update_time')*1000)}}
@js:var href = java.getString('@href')
```

难点是「当前节点」只有规则求值层知道，而沙箱是另一个 QuickJS 实例 ——
所以它走异步宿主桥（`__host.getString`），由 `analyze.ts` 把当前的 Selection 注进去。
第二个参数给了内容就在那段内容上求值，否则用当前节点。

**它有一个必须知道的限制：规则里不能再写 JS。** asyncify 不支持嵌套挂起 ——
从沙箱里再调进来一次会把挂起机制弄乱，所以含 `@js:` / `<js>` 的规则会直接报错，
而不是在深处以看不懂的方式炸掉。实测用法都是纯 JSONPath / 选择器，不受影响。

### `java.timeFormat(时间[, 格式])` / `java.timeFormatUTC(时间, 格式, 偏移)`

`时间` 是**毫秒**（书源自己把秒乘 1000）。格式串是 Java `SimpleDateFormat` 的模式，
默认 `yyyy-MM-dd HH:mm`。实现放在宿主侧（`src/lib/javatime.ts`），是纯函数，能直接做单元测试。

两个刻意的选择：

1. **`java.timeFormat` 默认按 +8 渲染。** Legado 里它用的是*设备本地时间*，
   而 Worker 跑在 UTC 上、也没有「用户的设备」可言；这些书源又是按中文安卓设备的
   本地时间写的。用 UTC 的话，晚上更新的书会显示成前一天。
   要别的时区就用 `java.timeFormatUTC(时间, 格式, 偏移)`，它的默认偏移是 0。
2. **不认识的记号按字面输出。** 只实现了 `y/M/d/H/h/m/s/S` 这几种；
   `E`（星期）、`a`（上午下午）、引号字面量都没做 —— 遇到就原样留着，
   而不是猜一个可能不对的值。`yyy` 也不会被拆成 `yy` + `y` 拼出「266」这种东西。

### `java.md5Encode` / `java.hexEncodeToString` / `java.hexDecodeToString`

书源拿它们拼鉴权签名：禁漫天堂API 的 token 是 `md5(时间戳 + 盐)`，
书音M 的目录接口要对地址做 md5。

**MD5 得自己实现 —— WebCrypto 不提供它**（弱摘要，标准里就没给）。
实现放在宿主侧（`src/lib/hash.ts`），走同步桥进沙箱，好处是它是纯函数：
单测直接拿 `node:crypto` 的 md5 逐条对拍，含空串、55/56/57 与 63/64/65 字节这些
补位边界，以及中文（MD5 必须按 **UTF-8** 取字节，按 UTF-16 会算出完全不同的值）。

两个 hex 助手也按 UTF-8 取字节，输出统一小写 —— 和 `md5Encode` 一致。

### 纯 UI 动作：`java.toast` / `java.longToast` / `java.refreshExplore`

服务端没有界面可弹，所以它们是 no-op —— **但必须有**。
书源里它们常和取数据写在同一个 `try` 里，缺一个就是「not a function」把整条规则带走，
而报错信息完全看不出是「弹个提示」这件事导致的。现在它们只往日志里写一行，
既不丢信息，也不让规则失败。`java.getWebViewUA` 同理，返回一个固定的安卓 WebView UA。

## 真实书源验证

拿一份社区的 18 条真实书源（yolo52/Yuedu 的 `shuyuan.json`）在本地逐条跑过搜索 → 详情 →
目录 → 正文。**书源不进仓库，验完即删。**

先说方言分布（按书源计）：`@js:` 15 条、正则 16 条、XPath 11 条、裸 CSS 1 条，
而 **JSOUP 默认规则 0 条**。也就是说自造的 fixture 站点里那套 `class.x.0@tag.a@href`
简写在真实书源里基本用不上，`@js:` 才是最主流的写法 —— 这直接决定了下面哪些缺口最要紧。

跑第一遍时 18 条里有 4 条「搜索成功」，但它们全都只用了 15～20 ms —— 那不可能是在访问外网。
查下去发现是打了 Worker 自己。这一步逼出了 3 个 fixture 站点永远测不出来的 bug，都已修：

| 修掉的 bug                                                   | 症状                                                                                                                        |
| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| 相对地址以「请求来源」而不是 `bookSourceUrl` 为基准          | 请求打到 Worker 自己，SPA 回退回 200 + 首页，规则从首页里抠出链接 —— 于是「搜索成功」但结果是本站的链接。**全程不报错**     |
| 裸 CSS 选择器（`.searchbook` / `div#content`）没被识别成 CSS | 被 JSOUP 解析器静默解成「取所有子节点」/「整页」，书籍链接变成整页导航的拼接。修完精华书阁从 1 条垃圾结果变成 20 条真实结果 |
| 请求选项要求严格 JSON                                        | `{'method': 'POST', ...}` 这种单引号写法被直接拒掉，而 Legado 用的是宽松解析器                                              |

修完之后的实测分布（同一批 18 条）：

| 结果                      | 条数 | 说明                                                      |
| ------------------------- | ---- | --------------------------------------------------------- |
| 搜索成功                  | 1    | 精华书阁 20 本（详情页规则未匹配，断在目录）              |
| 0 结果                    | 3    | 规则没匹配到，或站点已改版                                |
| `source is not defined`   | 2    | 缺沙箱全局                                                |
| `cookie is not defined`   | 3    | 缺沙箱全局                                                |
| 上游 403 / 404 / 网络错误 | 9    | 其中 6 条是因为 `searchUrl` 写成 `@js:`，被当成了字面地址 |

于是最要紧的三个缺口，按影响面排序：

1. **`@js:` 可以直接写在 URL 字段里**（`searchUrl`、`tocUrl` 等），整段是脚本、返回值才是地址。
   18 条里有 6 条这么写。目前会被当成字面地址去请求，得到一个必然 403/404 的 URL。
   这一条至少**会报错**，不像上面那两个是静默错数据。
2. **沙箱缺少 `source` 与 `cookie` 两个全局**。`source.key` / `source.getKey()` /
   `source.getVariable()` / `source.loginUrl` 分别出现在 5 条里，`cookie.removeCookie(...)`
   出现在 4 条里。这两个是 Legado 沙箱的基本设施，缺了它们，用这些写法的书源一条都跑不起来。
3. **`org.jsoup.Jsoup.parse(...)`**（3 条）：脚本里能直接用 Jsoup 选择器。
   引擎内部本来就有 cheerio，但没把它作为 `org.jsoup` 暴露进沙箱。

另有 3 条报 `internal error; reference = ...`（workerd 内部的错误，伴随超大响应头或
异常响应），**原因尚未查明** —— 没有把它算进上面的引擎缺口，因为还不能确定是我们的问题
还是 workerd 的限制。这是当前清单里唯一一处「不知道」的东西，单独列出来而不是含糊带过。

还有一处**本该更早发现的**：`nextContentUrl`（跨页章节）当初也只在类型里声明、代码从不读取。
一章被拆成多页的站点只会取到第一页 —— 表现是**「章节内容不全」**，
而它比报错更难察觉：页面看起来完全正常，只是少了一半。

实测数据（精华书阁同章）：第 1 页 1254 字，结尾「本章未完，请点击下一页继续阅读》》」；
第 2 页 1219 字，**结尾还是「本章未完」**；第 3 页之后还有。
只取第一页时读到 1208 字，取全后 3312 字 —— 也就是说之前**丢了一大半**。
现在按 `nextContentUrl` 逐页取回并接在一起，上限 10 页（一章通常 2～4 页）。

修这一条时又踩出一个更值得警惕的坑：**那个站点把「下一页」和「下一章」用了同一个 `id`**。
社区书源写的是 `nextContentUrl: "id.pb_next@href"`，跟着它走会从最后一页**跨到下一章**，
把后面几章的内容拼进当前章 —— 这比「内容不全」更糟，因为读到的根本不是这一章。
（当时一度看到"11059 字"，比单章正常长度大得多，才顺藤摸到这个问题。）

正确写法是**按文字取**：`nextContentUrl: "text.下一页@href"` ——
最后一页那个按钮写的是「下一章」，自然不匹配，于是干净地停下。
测试站点的分页正文特意复现了这个陷阱（末页挂一个共用 `id` 的「下一章」链接），
冒烟里断言「正文里不能出现下一章的内容」，免得以后有人把它改回按 id 取。

### 第二轮：为了真正读到书，又修了三个

第一轮只做到「能搜到」，一条都读不到正文。为了把其中一条真正跑通（见下），
又发现并修掉三个问题：

| 修掉的问题                             | 症状                                                                                                                                                                                                                 |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 地址类字段把多个匹配**拼成一个字符串** | 搜索条目里通常有多个 `<a>`（书名一个、最新章节一个），`bookUrl: a@href` 会把它们用换行拼起来；而 URL 解析器把换行当非法字符删掉，于是得到 `…/77706//77706//77706/65031092.html` 这种「看不出问题、永远打不开」的地址 |
| 目录分页（`nextTocUrl`）没实现         | 长书只显示第一页的 20 章。2226 章的书要 112 页 —— 这是「导入了书源却读不下去」的典型形态                                                                                                                             |
| `isJsoupShorthand` 漏了 `text` 关键字  | `text.下一页`（按文字找链接，真实书源就是用这个写翻页的）被误判成 CSS 选择器，直接失效                                                                                                                               |

顺带一个不是引擎问题的坑，值得写下来：**净化正则与取值方式必须配套**。同一个站点
`#nr1` 的 HTML 有 2821 字符却**一个换行都没有**（100 个 `<br>`），这时用 `@html` 取值再套
`##阅读提示.*`，正则会从「阅读提示」一路吃到结尾，正文只剩 24 个字；换成 `@textNodes`
取值（按 `<br>` 拆成多行）后，正则只删掉该删的那一行，正文 1208 字。
这不是 bug，是书源写法与站点结构不匹配 —— 但它的表现是「正文几乎为空」，很容易被当成引擎坏了。

`nextTocUrl` 的上限定在 20 页也不是随手写的：Workers 每次调用的子请求数（免费版 50 个）
和 CPU 时间都是硬限制，而每翻一页就是一次请求加一次解析。20 页约 400 章，留足余量；
要读更长的书得先上付费版再调大，而不是在这里赌平台会放过我们。

### 第三轮：媒体类源与接口型源

上线 816 条社区书源之后，「图片/音频/文件源读不出来」成了最集中的一类反馈。
按 `bookSourceType` 分流（见上文「媒体类书源」）是主要工作，但真正跑通一条真实音频源
（喜马拉雅）时，顺带挖出了一串**「不报错但什么都取不到」**的引擎问题 ——
这类问题比报错难查得多，因为表现统一是「搜不到书 / 目录是空的」：

| 修掉的问题                                           | 症状                                                                                                                                                                                        |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 图片/音频/文件一律走文本那条路                       | 图片源渲染成一屏 `<img>` 源码；音频源显示成一条网址；文件源报「未配置正文规则」——而下载地址在 `downloadUrls` 里从没被读过                                                                   |
| JSON 列表规则：数组字段不摊平                        | `bookList: "$.info.Datas"` 命中的是**整个数组**，不摊平就只有 1 个条目，内容是整段数组 JSON                                                                                                 |
| JSON 列表规则：条目沿用整页的 `source`               | 后续按 `$.name` 取字段等于在整页 JSON 的根节点上取键，所有条目字段全空 → **整条源搜不到书**。修完喜马拉雅从 0 本变 20 本、猫耳听书 0 → 30 本                                                |
| JSON 的**裸字段名**没被当成字段                      | `title`、`playPathAacv224‖playUrl64` 这种写法会去匹配同名 HTML 标签，而内容是一段 JSON → 目录一条都取不到。修完喜马拉雅目录从 0 章变 **400 章**                                             |
| 顶格 `@js:` 里的 `result` 绑成了空串                 | `ctx.result` 从来没被赋过值。图片源惯用的 `@js:result.indexOf('id="cp_img"')` 因此「执行成功但什么都取不到」；喜马拉雅的目录规则更直接：对空串 `JSON.parse` 就地报错                        |
| 地址字段取「第一个非空值」而不是「第一个非空**行**」 | `@js:` 返回地址数组时会按换行拼起来，整段拿去解析地址、换行又被 URL 解析器删掉，得到几条地址首尾相接的串（喜马拉雅的 `nextTocUrl` 拼出 9 条）→ 请求一个必然 404 的怪地址                    |
| 翻页中途失败会把**已拿到的整个目录丢掉**             | 一页 404 就让前面几百章全没了，用户看到错误页，而其实书是能读的。现在保留已有章节并在响应里带上 `warning`，前端显示「这份目录可能不完整」                                                   |
| 音频「直链」只有域名、没有路径也照样放行             | 猫耳听书的规则是 `'https://static.missevan.com/' + result`，`result` 取空时拼出光秃秃的域名；放行后变成一次无意义的代理请求、报 502，看不出真正原因。现在直接报「规则里拼接的字段没取到值」 |

实测结果（本地 dev server，逐条真实站点）：

| 书源                     | 类型 | 结果                                                             |
| ------------------------ | ---- | ---------------------------------------------------------------- |
| 喜马拉雅                 | 音频 | 搜到 20 本 / 目录 400 章 / 正文取到 m4a 直链，代取返回 206       |
| 猫耳听书                 | 音频 | 搜到 30 本 / 目录 9 章；正文因源规则本身取空而明确报错           |
| asmr（api.asmr-200.com） | 音频 | 搜到 20 本；书籍地址还没取到（用了 `{{$.id}}` 模板），下一轮修掉 |
| 老司机 / 天脉漫画        | 图片 | 搜索 0 条：站点改版或不提供搜索接口（`tnmm.cc` 已连不上）        |
| 爱书小说网               | 文件 | 搜索 0 条：站点返回的结果页里没有匹配项                          |

### 第四轮：字段模板与 JSONPath 过滤器

接着修 asmr 那条音频源。它的 `bookUrl` 是 `/api/tracks/{{$.id}}` —— 一条**字段模板**，
而当时字段规则里的 `{{}}` 根本不会被展开，所以书籍地址恒为空串（搜索能出 20 条，
点进去却「缺少 url 参数」）。把模板实现出来之后，又撞上它的 `chapterList`：

```
$..[?(@.type=="audio")]
```

递归下降 + 过滤器 —— 而过滤器当时是「明确抛错、不实现」。于是顺着把这两件事都做了。

| 修掉的问题                         | 症状                                                                                                                          |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| 字段规则里的 `{{...}}` 完全不展开  | `/api/tracks/{{$.id}}` 原样当选择器去筛 → 空串。asmr 的书籍地址、封面地址全是空的                                             |
| 展开之后仍被当成选择器             | 即使展开了，`/api/tracks/1593234` 也会被当选择器 → 还是空串。判断依据得是**骨架**，见「字段规则里的模板」                     |
| JSONPath 过滤器没实现              | `$..[?(@.type=="audio")]` 整条报「无法解析」，目录打不开。线上 816 条源里只有 4 条用到，共 8 处，全是「存在性」和「简单比较」 |
| `$..[` 这种写法不被词法分析接受    | 递归下降后面直接跟方括号，报「无法解析 JSONPath」                                                                             |
| 过滤器的等值比较按类型严格比       | 书源里 `@.id==1` 与 `"1"` 混着写，严格比会漏条目 —— 改成按字符串比                                                            |
| `&&` / `\|\|` 被切在方括号与引号里 | `$.list[?(@.a&&@.b)]` 被连接符从中间切开，报错信息指向半截规则（`过滤器缺少收尾的 )：$.list[?(@.a`），把人引错方向            |

修完 asmr 完整跑通（本地 dev server 实测）：搜索 20 本 → 目录 **26 章** → 正文取到音频直链 →
代取返回 206。在此之前它卡在第一步。

### 第五轮：沙箱助手

补上 `java.getString` / `java.timeFormat` / `java.timeFormatUTC` 三个助手
（见上文「沙箱助手」）。线上 **100 条**书源在用它们。

顺手把用这些助手的源逐条跑了一遍，结果值得记下来：**它们都不是被助手卡住的**，
而是各自撞在别的已知缺口上。这不是「助手没问题」的证明，但说明助手不是当前的主要瓶颈：

| 书源                   | 卡在哪                                                                                |
| ---------------------- | ------------------------------------------------------------------------------------- |
| ⚡📂听小说APP          | 章节地址规则里 `\|\|` 被切碎（第六轮已修）；另外还缺 `source` 全局与 `java.md5Encode` |
| 🎭🎬露西弗同人站       | 用了 `@JSon:`（大写 J），而前缀识别是大小写敏感的（后续计划第 2 条）                  |
| ⚡📂米读 / 七猫 / 书旗 | `searchUrl` 里直接写 `@js:`（老缺口）                                                 |
| 🌍🔞爱丽丝书屋         | 缺 `source` 全局                                                                      |
| 📂茶马 / ⚡📂听小说    | 站点列表可能是 JS 渲染的，`chapterList` 选择器没匹配到（静默 0 章）                   |
| 🔞爱腐文               | 同上：`chapterList` 没匹配到，目录 0 章、不报错                                       |

### 第六轮：JS 代码里的连接符

上一轮排查时发现的：`@js:` 代码里的 `||` / `&&` 会被当成规则的同级连接符切碎。
线上 816 条书源、19424 处规则里有 **321 处**连接符落在 JS 区域内部，三种形态都会中招
（见「分隔符不能切进 JS 与字面量里」）。

这一轮的收益能直接量出来：

| 书源            | 之前                                            | 之后                                                                                           |
| --------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 📂存书啦        | 正文取不到（规则被切碎）                        | 正文 **23894 字**                                                                              |
| 🎨🔞鸟鸟韩漫    | 目录打不开                                      | 目录 **22 章**                                                                                 |
| ⚡📂听小说APP   | 报 `expecting ','`（JS 语法错，看不出真正原因） | 报 `'source' is not defined`（真的缺什么）                                                     |
| 🔞🎨禁漫天堂API | 四条字段规则全被切碎                            | 规则不再被切开、能整段跑完（实测搜索 `ok`）；剩余是真实缺口：`jsLib` 自定义函数、`source` 全局 |

后两条才是这一轮最大的价值：**报错从「看不懂的语法错误」变成了「真正缺什么」**。
被切碎的规则会伪装成书源写错了，排查方向直接跑偏。

### 第七轮：接口型书源的列表规则

修完连接符之后，把线上媒体类源（12 条音频、71 条图片、9 条文件）逐条跑了一遍。
结论是「读不出来」不只是缺沙箱设施 —— 列表规则那条路上还压着**三个静默失败**
（见「列表规则：`@js:` 返回数组时」）：`@js:` 整条的列表规则被当成 JSOUP 简写、
数组结果被拍平成一条、条目的 `source` 绑到了整页。三处叠加就是
「接口明明返回了数据，却**一条都搜不到、而且不报错**」。

这一轮的收益同样能量出来：

| 书源            | 之前                                                   | 之后                                           |
| --------------- | ------------------------------------------------------ | ---------------------------------------------- |
| 🔊书音M         | 目录 0 章，报 `not a function`（缺 `java.md5Encode`）  | 目录 **14 章**、正文取到音频直链               |
| 🔊听友M         | 搜索 0 本（列表规则整条 `@js:` 被切）                  | 搜索 10 本 / 目录 **1389 章**、正文音频直链    |
| 🔊喜马拉雅      | 正文报「响应体积 5000951 字节，超过 4194304 字节上限」 | 正文取到 m4a 直链                              |
| 🔞🎨禁漫天堂API | 搜索 0 本、无报错                                      | 报 `'jmhost' is not defined`（真的缺 `jsLib`） |

顺带修的两处：

1. **响应体积上限 4 MiB → 16 MiB。** 这个上限是为了挡「被重定向到视频/下载页」，
   不是为了卡正文长度；喜马拉雅一章接口返回 5 MB JSON，正文直接读不出来，
   报的还是与书源无关的「体积超限」。
2. **补齐沙箱助手**：`java.md5Encode`、hex 互转，以及 `toast` / `longToast` /
   `refreshExplore` 这类纯 UI 动作 —— 它们必须是 no-op，但**不能没有**
   （见「沙箱助手」）。

剩下的失败大多不是引擎问题：站点改版、连不上、需要 WebView 渲染（`webView: true`）、
或落在已知缺口上（`@js:` 写在 URL 字段里、`java.getElements` / `setContent`、
`Packages.*` 的 Java 互操作、`source` / `cookie` 全局）。

### 第八轮：URL 字段里的 JS

上一轮把媒体类源跑完后，留在「已知缺口」第一条的就是它：**JS 直接写在 `searchUrl` 里**。
线上 85 条这么写（见「URL 字段里的 JS」），而当时的处理是把它**当成地址原文去请求** ——
请求的是 `https://站点/@js:var%20_o%20=%20%7B%7D;try…` 这种东西。

这一轮补齐后，同一批源的表现变化很直接（前 22 条逐条实测）：

| 书源            | 之前                                                | 之后                                                            |
| --------------- | --------------------------------------------------- | --------------------------------------------------------------- |
| 🎨漫蛙          | `@js:` 原文当地址 → 上游 404                        | 搜索到书                                                        |
| ⚡📂思路客      | 「java.ajax 不可用」（引擎没注入取网能力）          | 脚本跑通、发出真实请求（拿到上游 403 —— 站点的问题）            |
| 📂白鹿书院      | 脚本没跑，直接请求 `categories/1?name_cont=…` → 404 | 脚本跑通，报错精确到 `TypeError: not a function（脚本第 1 行）` |
| 🏷七猫小说 · API | 请求 `@js:qmSearch(key, page)` 原文                 | `ReferenceError: 'qmSearch' is not defined`（缺 `jsLib`）       |

后两条才是这一轮的价值：**失败从「地址看起来正常、请求也发出去了，只是结果不对」
变成了「明确告诉你缺什么、在第几行」**。

顺带把沙箱报错补上了错误类型与行号（原来是光秃秃一句 `not a function`，
书源脚本动辄几十行，根本定位不到）。剩下的 21 条失败所以能一眼归类：
`source` / `cookie` / `org` / 自定义 `jsLib` 函数（缺全局）、`java.put`（缺助手）、
连不上或站点已改版。

## 验证

```bash
npm install
npm run db:migrate   # 建本地 D1 表（首次、以及每次新增迁移后）
npm test             # 单元测试（178 项，Node 里毫秒级跑完；另有一个默认跳过的全量扫描，见下）
npm run dev          # 起本地服务，浏览器打开首页即可用；另开一个终端跑下面这条
npm run smoke        # 端到端：链路 + 书源管理 + 静态资源 + 书架 + 媒体 + 字段模板 + 沙箱助手 + 连接符切分 + 列表规则 + URL 字段 JS
```

单元测试只覆盖**纯函数**（规则解析、规则文本切分、位置选择、正则链、JSONPath、XPath 适配层、
导入校验、身份校验、图片地址提取、媒体签名、模板分类、时间格式化、MD5 摘要），因此能在 Node 里跑；
涉及 cheerio、QuickJS-WASM、D1 与前端静态资源的部分交给 `npm run smoke`
在**真实 workerd 运行时**里验证。两者分工明确，缺一不可：前者保证语义正确，后者保证运行时可跑。

内置测试站点（`/fixture/*`）是项目自己造的，不依赖任何第三方站点 —— 第三方站会改版、
会挂、在 CI 机房会被墙，拿它做回归会出现"今天绿明天红，却说不清是谁的问题"。

`npm run smoke` 分十八段，其中十四段值得单独说：

**多方言对照。** 内置站点配了六套书源 —— 分别用 `@css:`、XPath、`@js: + java.ajax`、
JSONPath、顶格 `@js:` 引用 `result`、字段 `{{}}` 模板六种规则写法打同一份数据。
六边的书名、作者、章节名、正文必须**逐字一致**。
只测一套的话，另外几条路径上的问题会被完全掩盖：XPath 的上下文节点与取属性、
`java.ajax` 的异步挂起、JSON 条目的 `source` 绑定、模板展开成字面值之后的走向
都是这么漏掉的。参与对照的方言**一个都不能少**：
某个源挂了就自动降级成两方比对，恰好会把挂掉那条路径放行，所以缺一个即判失败。

**字段规则模板。** 六种真实形态各验一遍：字面 + 模板（`《{{$.name}}》`）、
纯模板、模板 + 正则链、裸标识符走沙箱（`{{key}}`）、冗余 `@` 标记（`{{@@h1@text}}`）、
模板出现在 `##` 的查找串里。还有一条断言专用在 asmr 那个形状上：
`/fixture/book/{{$.id}}` 必须拼成一条正常地址 —— 它在修之前恒为空串。
另外验「不支持的复合过滤器必须报错」，而不是静默返回 0 条。

**沙箱助手。** `java.getString` 在模板里跑通 JSONPath、第二个参数换内容求值；
`java.timeFormat` 默认按 +8 渲染、`java.timeFormatUTC` 按显式偏移渲染
（拿固定时间戳断言，所以「差 8 小时」这种错跑不掉）；
`java.md5Encode` 与 hex 互转按已知向量断言；
`java.toast` / `refreshExplore` / `getWebViewUA` 必须在**同一条规则里连着出现**且不打断它 ——
它们本来就是 no-op，缺了却会让整条规则报 `not a function`；
「规则里再套 JS」必须明确报错 —— asyncify 不支持嵌套挂起，静默挂起会让整个请求悬住。

**列表规则返回数组。** 三种条目形态各验一遍，断言的都是**条目数与字段值**而不是「接口没报错」，
因为这条路上的失败全是静默的：`@js:` 返回 3 条 JSON 字符串必须得到 3 本书、
返回对象数组必须逐条 JSON 化（不能是 `[object Object]`）、返回 HTML 片段必须按 HTML 解析
让后续 CSS 字段规则可用。还有一条专门反证「条目的 `source` 绑对了没有」：
同一条目里的 `result` 必须解析出**该条目自己**的作者，而不是整页响应里的东西。

**URL 字段里的 JS。** 三种写法各来一条：整条 `@js:`（脚本里自己拼请求选项）、
整条 `<js>` 块（收尾表达式就是地址）、「地址 + 选项」再跟 `@js:`。
第三种让脚本自己检查它拿到的 `result` —— 必须既带请求选项、又是**没展开过**的 `{{key}}`，
形状不对就返回一个必然失败的地址，让断言红掉。
另有一条断言「URL 字段里的脚本能用 `java.ajax`」（取网能力没注入就报「java.ajax 不可用」），
以及一条「脚本出错要明确报错」—— URL 字段的失败模式是静默的，这一条比什么都重要。

**JS 里的连接符。** 拿真实书源原文当规则，验 `||` / `&&` 在 `@js:` 代码、`<js>` 块、
`选择器@js:` 加净化链这三处都不被切开。断言刻意做成「一旦被切开就必然失败」，
而不是「结果非空」—— 切开后的前半截往往仍是非空值，松断言会被蒙过去：
一条 `(java.getString('$.author') || '（无作者）') + '·已读'` 必须得到 `作者甲·已读`，
被切成两半时括号不配平，会直接炸成语法错误。

**图片 / 音频 / 文件源。** 三种媒体类型各自的返回形态、签名代取地址、代取回来的字节
与上游**逐字节一致**、`Range` 透传拿到 206 与正确的 `Content-Range`。
图片这一条还断言「取到的是真地址而不是 `src` 上的占位图」—— 测试站点刻意照抄了
真实漫画站的写法（`src` 放 1x1 透明 gif、真地址在 `data-src` 上），因为取错的话
一章几十张图会全变成同一张空白图，**看起来像加载成功**。
另外还验了代取接口不是开放代理：签名被改、没签名、直接把 URL 当参数，都必须 403。

**书源管理的往返。** 导入 → 列表 → **用导入进来的源真的搜一次** → 重复导入 →
坏输入被拒 → 停用 → 删内置源被拒 → 删除。其中「用导入进来的源真的搜一次」是关键 ——
书源从库里读出来还能驱动整条链路，才是 D1 这部分真正要证明的事。

**静态资源与接口的路由顺序。** 静态资源是「先查资源、匹配不到才进 Worker」，
接口必须反着来。这两条规则配错的表现是「页面能开、接口全 404」或者「接口正常、
页面却是接口的 404」，都极容易被误判成前端写错了 —— 所以这里直接钉住：
未命中的 `/api/*` 必须回 JSON 404，而不是被 SPA 回退喂成 200 + HTML。
这一条加进去的当天就抓到了真问题：兜底路由把 `/api/*` 也一起兜走了，
`notFound` 根本轮不到，未命中的接口返回的是 HTML。

这几段都会自己清理，重复运行不会在库里越积越多。

### 用真实书源全量扫描

冒烟跑的是内置站点 —— 它证明「运行时可跑」，但证明不了「线上 800 多条书源里没有漏网的」。
有些结论只能拿整份集合去量，典型的就是「连接符不切进 JS」：单测钉住的是几十条精选形态，
而线上到底有多少处落在 JS 区域里、有没有一处被切开，只有全量扫才知道。

```bash
# 导出一份书源（wrangler --json 的原样输出即可，也接受裸数组）
npx wrangler d1 execute reader-cloudflare --remote --json \
  --command "SELECT name, payload FROM sources" > sources.json
SOURCES_DUMP=sources.json npx vitest run test/ruleSplitting.scan.test.ts
```

**默认整组跳过**，所以 CI 与日常 `npm test` 不受影响，书源也不会进仓库。
它同时断言两个方向：没有 JS 区域被切开（321 处受保护）、也没有规则被过度保护
（1022 处该切的仍然照切）。两个方向缺一个，结论都不成立 ——
只查「没切开」的话，区域识别整个失效时会**空过**。

**相对地址的基准。** 正例：相对 `searchUrl` 能按 `bookSourceUrl` 正常解析。
反例（这条才是关键）：把 `bookSourceUrl` 指到一个没人监听的端口，搜索**必须失败**，
且错误里要出现那个主机名。修之前这条会「成功」地返回本站首页里的链接 ——
反例不成立，正例再绿也说明不了问题。

**裸 CSS 选择器。** 用 `.result-item`、`h3.title@text`、`#content@textNodes`
（全都不带 `@css:` 前缀、也不是 `class.`/`tag.` 简写）从搜索一路走到正文。
修之前列表规则会圈错条目、书籍地址会变成整页链接的拼接，所以这里断言的是
「条目数正确」和「书籍地址是一条正常地址」。

**地址字段只取一个值。** 测试站点的搜索条目现在带两个链接（书名 + 最新章），
正好复现真实书源那个坑。断言的是「书籍地址等于第一个链接」且「两本书地址互不相同」——
只看「能搜到」是发现不了这个问题的，因为拼出来的地址不报错、只是打不开。

**分页目录。** 测试站点造了一份确定的两页目录（第 1 页 1 章 + 「下一页」，第 2 页 2 章），
断言两页被合并成 3 章、顺序正确、无重复。三种翻页写法各验一遍：
`text.下一页@href`（按文字找链接，绝大多数站点这么写）、
`@js:` 返回**地址数组**（接口型站点一次给出后面所有页，喜马拉雅就是这样）、
以及「下一页失效」——此时应当**保留已拿到的章节**并回一个 `warning`，
而不是把整份目录丢掉。第二种如果不当回事，几条地址会被 URL 解析器粘成一条，
「只取第一页」于是伪装成「上游报错 404」。

**分页正文。** 测试站点把一章拆成两页（第 1 页 2 段 + 「下一页」，第 2 页 1 段），
断言「两页拼起来的正文与单页正文**逐字一致**」。
这里刻意不用「长度大于多少字」这种松断言 —— 章节内容不全的问题恰恰是
「看起来正常、只是少了一半」，松断言根本拦不住。

沙箱（cheerio、QuickJS-WASM）与 D1 **没有单元测试**：前者依赖 `.wasm` 的打包器导入，
后者需要绑定，Node 里都跑不起来。这部分覆盖完全由 `npm run smoke` 承担，
所以它断言得很细（含 `java.ajax` 二次取数后的正文逐字比对）。

前端的**交互逻辑没有自动化覆盖**：`smoke` 只保证资源能取到、接口契约正确，
不等于点了按钮都对。改前端时请手点一遍四条主路径（书架 / 搜索 / 书源 / 阅读）。

## CI

`.github/workflows/ci.yml` 在推送到 `main` 和 PR 时跑：装依赖 → 建本地 D1 表 →
类型检查 → 格式检查 → 单元测试 → 端到端冒烟。同一分支连续推送会取消上一次未跑完的任务。

两处值得说明的写法：

**起服务与冒烟放在同一个 step。** Actions 里跨 step 启动的后台进程不可靠 ——
step 结束时它可能被连带杀掉，于是冒烟打不到服务。所以一个 step 里起、探测、测、收。

**等就绪靠探测而不是睡固定秒数。** 机器忙的时候固定秒数必然不够，机器闲的时候又白等。
循环打 `/api/health`，通了才往下走；真起不来就把 `wrangler.log` 贴出来，
否则失败时只剩一句「断言没过」，看不出是代码问题还是服务根本没起来。

还有一条容易踩的：`.dev.vars` 是本地开发文件、不入库，CI 里要现造一份把测试站点打开，
否则书源列表是空的，冒烟会在一开始就全挂。

## 接口

前端只用这些接口，换个客户端也不必改后端：

| 方法   | 路径                | 说明                                                                  |
| ------ | ------------------- | --------------------------------------------------------------------- |
| GET    | `/api/probe`        | 运行时自检：cheerio、QuickJS、D1 各探一次                             |
| GET    | `/api/sources`      | 书源列表（含是否启用、是否内置）                                      |
| POST   | `/api/sources`      | 导入书源，请求体是 Legado JSON 原文                                   |
| PATCH  | `/api/sources`      | `{id, enabled}` 启用 / 停用                                           |
| DELETE | `/api/sources`      | `?id=` 删除                                                           |
| POST   | `/api/search`       | `{keyword, sourceIds?}` 聚合搜索，按源返回结果与错误                  |
| GET    | `/api/book`         | `?sourceId=&url=` 书籍详情（主要拿目录地址）                          |
| GET    | `/api/toc`          | `?sourceId=&url=` 目录；翻页中途失败时多带一个 `warning`              |
| GET    | `/api/content`      | `?sourceId=&url=` 正文，`kind` 为 `text`/`images`/`audio`/`downloads` |
| GET    | `/api/media/:token` | 媒体代取。`token` 由 `/api/content` 签发，**只认自己签的地址**        |
| GET    | `/api/shelf`        | 书架（带出阅读位置）。**需身份头**                                    |
| POST   | `/api/shelf`        | 加入书架，重复加入只更新不新增。**需身份头**                          |
| DELETE | `/api/shelf`        | `?key=` 移出书架（进度一并清掉）。**需身份头**                        |
| GET    | `/api/progress`     | `?sourceId=&bookUrl=` 阅读位置。**需身份头**                          |
| PUT    | `/api/progress`     | 记录阅读位置（不需要先进书架）。**需身份头**                          |

身份头是 `x-reader-user`，值是一串 20～64 位的 URL 安全字符；
不带或格式不对一律返回 `400 missing_identity`（不会退回成某个默认用户）。

失败一律回 `{ error, code }`，`code` 是机器可读的（`invalid_json`、`sandbox_error`、
`upstream_error`、`builtin_readonly`、`shelf_entry_not_found` 等），前端据此分支处理。

## 部署

```bash
npm run db:migrate:remote   # 建线上表
npm run deploy              # 需要先 npx wrangler login
```

**线上实例：<https://reader-api.liujieahu.workers.dev>**

D1 库（`reader-cloudflare`，APAC）与线上表都建好了，Worker 已部署。
换账号部署时先 `npx wrangler d1 create <名字>`，再把新的 `database_id` 填进 `wrangler.jsonc`。

### 刚部署完是「空的」，这是对的

新部署实例的书源列表是空的 —— 库里一条书源都没有，所以什么都搜不到、书架也是空的。
这不是故障：本项目不分发书源，第一次用必须自己去「书源」页导入一份 Legado 书源 JSON。

页面对这两种情况是**分开提示**的：一个书源都没有时说的是「先在书源里导入」，
而书源正常但没搜到结果时说的是「没搜到」。搜索接口为此专门回了 `sourceCount`，
前端才能区分这两件事 —— 把它们混成一句「没有结果」，用户会一直以为是站点出了问题。

`ENABLE_FIXTURE` 线上保持 `false`（默认值），它是测试内容，不该对外提供。
线上已验证 `/fixture/*` 确实拿不到测试站点内容。

部署后建议先打一遍 `/api/probe`：它一次性回答三个最容易出问题的地方 ——
cheerio 能不能解析、QuickJS 的 WASM 能不能在线上加载、D1 绑定有没有连上。

## 关于书源

本项目**不提供、也不分发任何书源**。规则引擎是中立的工具，指向哪个站点、抓取什么内容，
由使用者自行决定并自负其责 —— Legado、any-reader 这些项目也都是这么划线的。

请遵守目标站点的服务条款与 robots 协议，并注意所在地区的版权法规。
项目自带的"内置测试站点"只包含项目自己生成的内容，用于验证链路。

## 后续计划

1. **补齐沙箱的 Legado 设施** —— 这是当前最影响可用性的一处，按实测影响面排序：
   `source` 与 `cookie` 两个全局（URL 字段脚本里出现最多）、书源的 `jsLib` 全局函数库
   （七猫、禁漫天堂API、阅文整条规则都建立在它上面）、`org.jsoup.Jsoup`、
   以及 `java.put` / `java.get` 这类缓存助手。这几项补齐之前，社区书源里能跑通的比例会一直很低
2. **规则前缀的大小写** —— `@JSon:`（大写 J）现在不会被认成 JSONPath，
   会被当成选择器然后静默返回空。真实书源里确实有这种写法（🎭🎬露西弗同人站）。
   修起来是几行，但它改的是**所有规则的分派**，所以单独一轮做更稳妥
3. **沙箱还缺的 `java` 助手与 Java 互操作** —— `java.getElements` / `java.setContent`
   （快看漫画的目录就卡在这两个上）、`java.t2s`（繁转简）、`java.createSymmetricCrypto`（AES）、
   以及 `Packages.*`（`BitmapFactory`、`Cipher`、`ByteArrayOutputStream`…）。
   它们和 `imageDecode` 是同一类：都需要一个能在沙箱里用的 Java 运行时替身。
   缺的时候是「明确报错」，不是静默返回空
4. **XPath 的取值后缀** —— 真实书源里有 `.//a[text()="下一页"]/../../div[3]@html`
   这种写法（XPath 末尾接 Legado 的取值后缀）。目前会被整段当成 XPath 表达式，
   报 `XPath parse error`。难处在于 `@href` 到底是属性还是取值后缀本身有歧义，
   需要先定清楚规则再动手 —— 猜错的代价是静默取到错数据
5. **JSONPath 的复合过滤器** —— `?(@.a&&@.b)` 现在会明确报错。
   线上 816 条源里一处都没有，所以暂不实现；真遇到时至少报错说清是哪一种不支持
6. **XPath → 名称规范化** —— 目前元素名保持小写（htmlparser2 原样），`//DIV` 匹配不到；
   书源里都是小写写法，暂不处理
7. **图片源的 `imageDecode`** —— 少数漫画源（71 条里有 5 条）用 JS 对图片重新切片来打乱顺序，
   靠的是 Android 的 `BitmapFactory` / `Canvas`。Workers 上没有这些，短期内做不了，
   遇到时上层会明确报错而不是显示一张错位的图
8. **`选择器@js:` 里 `result` 的形态** —— 选择器命中多个值时，引擎把 `result` 绑成**数组**，
   而相当一部分书源是按**换行分隔的字符串**写的。🎨🔞鸟鸟韩漫 的正文就是
   `class.view-imgBox@tag.img@data-src` 后面接 `@js: … result.split('\n') …`，
   数组没有 `.split`，于是报 `TypeError: not a function`（脚本第 4 行），整章图都读不出来。
   Legado 在「取字符串」的字段上给的是拼好的字符串，按字符串写的书源才是多数；
   但反过来也有按数组写的（`result[result.length - 1]`、`result[0]`）。
   所以不能简单改绑定 —— 先要把 Legado 的规则定清楚，再用全量扫描确认两边各有多少条
9. **阅读体验** —— 目录内搜索、书签、阅读历史

（原先列在这里的「查清 `internal error; reference = ...`」已经查清，见上文「真实书源验证」：
从本机直连同样失败、各卡 10 秒超时，属于站点/链路层面的问题被 workerd 包了一层，
不是引擎的锅，因此不再作为待办。）

## 许可

**AGPL-3.0-or-later**。`LICENSE` 就是 AGPL-3.0 的标准原文，一个字没改，
与 SPlayer 项目里那份**内容完全相同**（`git hash-object LICENSE` 两边都是
`dbbe3558157f5861bff35dcb37b328b679b0ccfd`）。
不各留一份「填好项目名的变体」，是为了让「用的是哪个许可」这件事没有解释空间。

`package.json` 里的 SPDX 标识与 SPlayer 保持同一个值：`AGPL-3.0-or-later`，
**不是** `AGPL-3.0-only`。一个 `-or-later` 一个 `-only` 看着只差几个字母，
法律含义却不同：`-only` 不允许被许可方选用后续版本，`-or-later` 允许。
AGPL 原文附录里给的样板声明本身就是「or (at your option) any later version」，
两个项目统一按 -or-later 走。

选 AGPL 而不是 MIT，是因为这是个**网络服务**：AGPL 比 GPL 多出的那一条（第 13 条），
正是用来挡住「拿去做闭源 SaaS」—— 规则引擎这类东西被闭源套壳的风险不低，
而 MIT 允许别人改完闭源、连改动都不必回馈。

### 部署时必须注意的一条

AGPL 第 13 条要求：**用户通过网络与这个程序交互时，必须能拿到它的源代码。**
这不是「建议」，是许可生效的前提。所以前端页脚里放了一个「源代码」链接，
指向 <https://github.com/hashiqi12138/reader-cloudflare>（公开仓库，已有全部历史）。

这条义务还加了一道防线：`npm run smoke` 会断言首页里存在这个链接，
删掉它 CI 就会红。许可义务靠「记得」是保不住的，得让它变成会失败的检查。

改仓库名或换地址时，记得同步改 `public/index.html` 页脚里那一个链接：
链接失效等于没履行，而「忘了放链接」属于许可违规，不是疏忽。

另外，AGPL 只约束**本项目的代码**，不改变上面「关于书源」那一条：
本项目依然不提供、也不分发任何书源。
